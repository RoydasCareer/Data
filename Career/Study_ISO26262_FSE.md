# Part 1: ISO 26262 기초

## 1.1 ISO 26262란

**ISO 26262: Road Vehicles — Functional Safety**

자동차 전기/전자 시스템의 기능 안전(Functional Safety)을 다루는 국제 표준입니다.
IEC 61508 (산업용 기능 안전 표준)을 자동차 도메인에 특화하여 개발되었습니다.

### 발전 역사

| 연도 | 사건 |
|------|------|
| 2000년대 초 | 자동차 전장 시스템 복잡도 급증 |
| 2011 | ISO 26262 초판 발행 (12개 파트) |
| 2018 | ISO 26262 2판 발행 (현재 버전, 12개 파트) |

### 적용 범위

- **대상:** 최대 총 중량 3,500kg 이하의 승용차 E/E 시스템
- **포함:** 하드웨어, 소프트웨어, 시스템 레벨 모두
- **제외:** 트럭/버스 (별도 표준 적용), 순수 기계적 시스템

---

## 1.2 기능 안전(Functional Safety)이란

**기능 안전** = 기능 오동작(Functional Malfunction)으로 인한 불합리한 리스크의 부재

```
기능 안전 ≠ 기능적 정확성
기능 안전 = 안전 관련 결함이 위험을 초래하지 않도록 보장
```

### 안전과 관련된 용어

| 용어 | 정의 | 예시 |
|------|------|------|
| **Hazard (위험원)** | 해를 끼칠 수 있는 원인 | 브레이크 오작동 |
| **Harm (해)** | 사람에게 발생한 신체적 피해 | 사망, 부상 |
| **Risk (리스크)** | 위험 발생 가능성 × 피해 심각도 | |
| **Safety Goal (안전 목표)** | 허용 불가능한 위험을 피하기 위한 최상위 요구사항 | |
| **Hazardous Event** | 특정 운전 상황에서의 위험원 발생 | 주행 중 갑작스러운 가속 |

# Part 2: ASIL (Automotive Safety Integrity Level)

## 2.1 ASIL이란

ASIL은 안전 기능에 요구되는 리스크 감소 수준을 나타냅니다.
위험 분석 및 리스크 평가(HARA)의 결과로 결정됩니다.

| ASIL | 의미 | 대표 시스템 |
|------|------|-----------|
| QM | Quality Management (안전과 무관) | 엔터테인먼트 시스템 음량 |
| ASIL A | 최저 안전 수준 | 방향 지시등 |
| ASIL B | 낮은 안전 수준 | 파워 윈도우 |
| ASIL C | 높은 안전 수준 | 에어백 점화 |
| ASIL D | 최고 안전 수준 | ABS, EPS(전자식 파워 스티어링) |

---

## 2.2 ASIL 결정 방법 (HARA)

### HARA (Hazard Analysis and Risk Assessment)

위험원을 분석하고 리스크를 평가하여 ASIL을 결정하는 과정입니다.

**3가지 파라미터:**

### 심각도 (Severity, S)

| 등급 | 설명 | 예시 |
|------|------|------|
| S0 | 부상 없음 | 불편함만 발생 |
| S1 | 경상 | 가벼운 부상 |
| S2 | 중상 | 중증 부상, 생존 가능 |
| S3 | 사망 또는 생존 불가능한 부상 | 사망 |

### 노출도 (Exposure, E)

| 등급 | 설명 | 예시 |
|------|------|------|
| E0 | 매우 낮은 가능성 | 거의 발생하지 않음 |
| E1 | 매우 드물게 | 차량 수명 중 1번 미만 |
| E2 | 드물게 | 차량 수명 중 1~2번 |
| E3 | 중간 | 가끔 발생 |
| E4 | 높은 빈도 | 대부분의 운전 시간 |

### 제어 가능성 (Controllability, C)

| 등급 | 설명 | 예시 |
|------|------|------|
| C0 | 일반적으로 제어 가능 | 99% 이상 제어 가능 |
| C1 | 단순하게 제어 가능 | |
| C2 | 보통 제어 가능 | 대부분 제어 가능 |
| C3 | 어렵게만 제어 가능 | 일반 운전자 제어 어려움 |

### ASIL 결정 테이블

|  | C1 | C2 | C3 |
|--|----|----|-----|
| **S1 E1** | QM | QM | QM |
| **S1 E2** | QM | QM | QM |
| **S1 E3** | QM | QM | A |
| **S1 E4** | QM | A | B |
| **S2 E1** | QM | QM | QM |
| **S2 E2** | QM | QM | A |
| **S2 E3** | QM | A | B |
| **S2 E4** | A | B | C |
| **S3 E1** | QM | QM | A |
| **S3 E2** | QM | A | B |
| **S3 E3** | A | B | C |
| **S3 E4** | B | C | D |

**예시 계산:**
브레이크 시스템 오작동:
- S3 (사망 가능성)
- E4 (항상 주행 중 사용)
- C3 (제어 거의 불가)
→ ASIL D

---

## 2.3 ASIL 분해 (ASIL Decomposition)

높은 ASIL 요구사항을 두 개의 독립적인 채널로 분산하여 낮출 수 있습니다.

```
ASIL D
   ↓ 분해
ASIL C (채널 A)  +  ASIL A (채널 B)
또는
ASIL B (채널 A)  +  ASIL B (채널 B)
```

**조건:** 두 채널은 **독립적(Independent)**이어야 합니다.
공통 원인 고장(Common Cause Failure)이 없어야 합니다.

# Part 3: 안전 수명주기 (Safety Lifecycle)

## 3.1 전체 안전 수명주기

```
1. 개념 단계 (Concept Phase — Part 3)
   ├── 항목 정의 (Item Definition)
   ├── HARA (Hazard Analysis and Risk Assessment)
   └── FSC (Functional Safety Concept)

2. 시스템 레벨 개발 (Part 4)
   ├── TSC (Technical Safety Concept)
   └── 시스템 설계

3. HW 레벨 개발 (Part 5)
   └── HW 아키텍처, HW 설계

4. SW 레벨 개발 (Part 6)  ← 수환씨 핵심
   ├── SW 안전 요구사항
   ├── SW 아키텍처
   ├── SW 설계 및 구현
   └── SW 검증

5. 생산/운영/서비스 (Part 7)

6. 폐기 (Decommissioning)
```

---

## 3.2 개념 단계 (Part 3) 상세

### 항목 정의 (Item Definition)

안전을 평가할 대상을 명확히 정의합니다.

```
항목(Item) = 시스템 또는 그 조합 (SW+HW+기계)
예시: ABS 시스템 전체
     EPS (Electric Power Steering) 시스템
     IVI 시스템 (QM이지만 ADAS와 인터페이스 시 주의)
```

### FSC (Functional Safety Concept)

HARA에서 도출된 안전 목표(Safety Goal)를 달성하기 위한 기능 안전 요구사항.

```
Safety Goal: "의도치 않은 가속이 없어야 한다"
     ↓ 분해
Functional Safety Requirement:
  - 엑셀 페달 위치 센서가 오작동 시 엔진 출력을 제한해야 한다
  - 두 개의 독립적인 센서가 상호 확인해야 한다
```

---

## 3.3 SW 레벨 개발 (Part 6) — 가장 중요

### SW 안전 요구사항

FSC와 TSC에서 도출된 소프트웨어 안전 요구사항을 정의합니다.

**요구사항 특성:**
- 명확하게 (Unambiguous)
- 완전하게 (Complete)
- 검증 가능하게 (Verifiable)
- 추적 가능하게 (Traceable)

### SW 아키텍처 설계

| ASIL 요구사항 | 설계 원칙 |
|-------------|----------|
| 모듈성 | 안전 관련/비관련 소프트웨어 분리 |
| 계층적 구조 | 명확한 인터페이스 |
| 단순성 | 복잡성 최소화 |
| 리소스 관리 | 메모리, CPU 사용 제어 |

### SW 검증 요구사항 (Part 6, Clause 9)

**ASIL별 테스팅 요구사항:**

| 기법 | ASIL A | ASIL B | ASIL C | ASIL D |
|------|--------|--------|--------|--------|
| 구문 커버리지 | ++ | ++ | + | + |
| 분기 커버리지 | + | ++ | ++ | + |
| MC/DC 커버리지 | o | + | ++ | ++ |

기호: ++ = 강력 권고, + = 권고, o = 선택

# Part 4: 하드웨어 신뢰도 (Part 5)

## 4.1 하드웨어 아키텍처 메트릭

ISO 26262 Part 5는 HW 아키텍처가 랜덤 HW 결함을 감지/제어하는 능력을 측정합니다.

### PMHF (Probabilistic Metric for Hardware Failures)

| ASIL | PMHF 목표값 |
|------|-----------|
| ASIL A | < 10^-7 /h |
| ASIL B | < 10^-7 /h |
| ASIL C | < 10^-8 /h |
| ASIL D | < 10^-8 /h |

### SPFM (Single Point Fault Metric)

단일 고장으로 인해 안전 목표가 위협받을 수 있는 비율:

| ASIL | SPFM 목표값 |
|------|-----------|
| ASIL B | ≥ 90% |
| ASIL C | ≥ 97% |
| ASIL D | ≥ 99% |

### LFM (Latent Fault Metric)

숨겨진 결함이 다른 결함과 조합되어 위험을 초래할 수 있는 비율:

| ASIL | LFM 목표값 |
|------|----------|
| ASIL B | ≥ 60% |
| ASIL C | ≥ 80% |
| ASIL D | ≥ 90% |

# Part 5: 안전 분석 기법

## 5.1 FMEA (Failure Mode and Effects Analysis)

**고장 모드 및 영향 분석**

각 컴포넌트의 고장 모드를 식별하고 그 영향을 분석합니다.

### FMEA 테이블 구조

| 컴포넌트 | 고장 모드 | 영향 | 심각도 | 현재 제어 수단 | RPN |
|---------|---------|------|--------|-------------|-----|
| 브레이크 압력 센서 | 값 고착 (High) | 브레이크 압력 과다 | S3 | 중복 센서 | 높음 |
| 브레이크 압력 센서 | 신호 없음 | 브레이크 작동 안 됨 | S3 | 진단 모니터링 | 매우 높음 |

**RPN (Risk Priority Number) = 심각도 × 발생도 × 감지도**

---

## 5.2 FTA (Fault Tree Analysis)

**고장 트리 분석**

톱 레벨 위험(Top Event)에서 시작하여 원인을 역추적합니다.

```
[Top Event: 차량이 의도치 않게 가속]
          OR
    [엑셀 ECU 오작동] AND [안전 모니터링 실패]
    
[엑셀 ECU 오작동]
     OR
[소프트웨어 버그] OR [하드웨어 고장]
```

**FTA 기호:**
- OR 게이트: 하나라도 발생하면 상위 이벤트 발생
- AND 게이트: 모두 발생해야 상위 이벤트 발생

---

## 5.3 FMEA vs FTA 비교

| 특성 | FMEA | FTA |
|------|------|-----|
| 분석 방향 | 상향식 (Bottom-up) | 하향식 (Top-down) |
| 시작점 | 컴포넌트 고장 | 시스템 위험 |
| 결과 | 고장 영향 목록 | 고장 원인 트리 |
| 장점 | 모든 고장 모드 체계적 검토 | 복합 원인 분석 |

# Part 6: 안전 케이스 (Safety Case)

## 6.1 안전 케이스란

안전 목표가 달성되었음을 구조적으로 논증하는 문서입니다.

```
안전 케이스 = 클레임 + 증거 + 논증
```

**구조 예시 (GSN — Goal Structuring Notation):**

```
[안전 목표: 의도치 않은 가속 없음]
         ↓ 논증
[센서 중복성으로 단일 고장 탐지]
     ↓ 증거
[FMEA 결과]  [FTA 결과]  [테스트 결과]
```

## 6.2 DIA (Development Interface Agreement)

OEM과 공급업체 간의 안전 책임 분담 계약서.

```
OEM 책임: 시스템 레벨 HARA, Safety Goal 정의
Tier1 책임: 소프트웨어 ASIL 요구사항 구현 및 검증
```

# Part 7: 기능 안전 관리 (Part 2)

## 7.1 안전 문화 (Safety Culture)

ISO 26262 Part 2는 조직의 안전 문화와 관리를 다룹니다.

**핵심 요소:**
- 경영진의 안전 의지
- 안전 담당자 임명 (Safety Manager, FSM: Functional Safety Manager)
- 안전 교육
- 안전 감사

## 7.2 기능 안전 감사 (Functional Safety Audit)

프로세스가 안전 계획을 따르는지 확인하는 활동.

**vs 기능 안전 평가 (Functional Safety Assessment):**

| 구분 | 감사 (Audit) | 평가 (Assessment) |
|------|------------|-----------------|
| 목적 | 프로세스 준수 확인 | 안전 목표 달성 여부 확인 |
| 시점 | 개발 중 | 주요 마일스톤 |
| 수행자 | 내부 QA 또는 독립 감사팀 | 독립 안전 전문가 |

# Part 8: 지원 프로세스 (Part 8)

## 8.1 형상 관리 (Configuration Management)

안전 관련 항목의 버전과 변경을 관리합니다.

**요구사항:**
- 모든 안전 관련 산출물의 버전 관리
- 변경 승인 프로세스
- 안전에 미치는 영향 평가 (Safety Impact Analysis)

## 8.2 변경 관리 (Change Management)

안전 관련 변경은 반드시:
1. 변경 영향 분석 (포함: ASIL 재평가 필요 여부)
2. 회귀 테스팅
3. 안전 케이스 갱신

# 빠른 참조 카드

## ASIL 결정 암기

```
S × E × C → ASIL

S3 + E4 + C3 = ASIL D (브레이크, 조향)
S3 + E4 + C2 = ASIL C (에어백)
S2 + E4 + C2 = ASIL B (파워 윈도우)
S1 + E4 + C2 = ASIL A (방향 지시등)
QM = 안전과 무관
```

## ASIL 분해

```
ASIL D → ASIL C + ASIL A
ASIL D → ASIL B + ASIL B
ASIL C → ASIL B + ASIL A
(독립성 필수)
```

## ASIL별 커버리지

```
ASIL A: 구문 커버리지 ++
ASIL B: 분기 커버리지 ++
ASIL C: MC/DC ++
ASIL D: MC/DC ++ (강력 필수)
```

## ISO 26262 파트 요약

```
Part 2: 안전 관리 (FSM, Safety Culture)
Part 3: 개념 단계 (HARA, Safety Goal, FSC)
Part 4: 시스템 레벨 (TSC)
Part 5: HW 레벨 (SPFM, LFM, PMHF)
Part 6: SW 레벨 (SW 요구사항, 아키텍처, 검증)
Part 8: 지원 프로세스 (형상관리, 변경관리)
Part 9: ASIL 결정 방법
```

## FMEA vs FTA

```
FMEA: Bottom-up, 컴포넌트 → 시스템
FTA:  Top-down, 시스템 위험 → 원인
```

## 안전 수명주기 순서

```
항목 정의 → HARA → Safety Goal → FSC
→ TSC → HW/SW 개발 → 검증 → Safety Case
```

## 수환씨 경험 → ISO 26262 활용

```
IVI SW 버전 검증     → Part 6 SW 검증
OTA 후 회귀 테스팅   → 변경 관련 테스팅
ADAS 경고 기능 테스팅 → 인터페이스 안전 (ASIL 할당)
FPT Korea ↔ 현대     → DIA (OEM-Tier1 안전 책임)
```
