# Part 1: A-SPICE 기초 개념

## 1.1 A-SPICE란

**Automotive SPICE (Software Process Improvement and Capability dEtermination)**

자동차 소프트웨어 개발 프로세스의 품질을 평가하고 개선하기 위한 모델입니다.
ISO/IEC 33000 시리즈(구 ISO 15504, SPICE)를 자동차 도메인에 맞게 적용한 것입니다.

### 역사와 배경

| 연도 | 사건 |
|------|------|
| 1994 | ISO 15504 (SPICE) 초안 개발 시작 |
| 2005 | HIS (독일 OEM 협회)가 자동차용 프로세스 평가 모델 발표 |
| 2010 | Automotive SPICE 공식 명칭 사용 |
| 2017 | PAM v3.1 발표 (현재 버전) |
| 2023 | v4.0 업데이트 논의 중 |

### 왜 필요한가

OEM은 Tier1 공급업체의 소프트웨어 개발 프로세스 품질을 확인해야 합니다.
BMW, VW, Daimler 등 독일 OEM들은 **Tier1에게 A-SPICE Level 2 또는 3 요구**합니다.

```
OEM 요구사항: "당신의 SW 개발 프로세스가 ASPICE Level 2 이상임을 증명하라"
Tier1 대응: A-SPICE 평가 실시 → 결과 OEM에 제출
```

## 1.2 프로세스 참조 모델 (PRM)과 프로세스 평가 모델 (PAM)

### 두 가지 모델

| 모델 | 역할 |
|------|------|
| **PRM (Process Reference Model)** | "무엇을"해야 하는가 — 프로세스 정의 |
| **PAM (Process Assessment Model)** | "얼마나 잘" 하는가 — 평가 기준 |

A-SPICE PAM v3.1은 PRM과 PAM을 통합하여 제공합니다.

## 1.3 프로세스 그룹 (Process Groups)

A-SPICE PAM v3.1에는 다음 프로세스 그룹이 있습니다:

```
자동차 HW 관련 프로세스 (HWE)
자동차 SW 관련 프로세스 (SWE) ← 핵심
시스템 엔지니어링 프로세스 (SYS)

관리 프로세스 (MAN)
프로세스 개선 프로세스 (PIM)
재사용 프로세스 (REU)
```

# Part 2: 능력 수준 (Capability Levels)

## 2.1 6단계 능력 수준

A-SPICE는 각 프로세스에 대해 0~5 수준으로 능력을 평가합니다:

| 레벨 | 이름 | 핵심 의미 |
|------|------|----------|
| **0** | Incomplete | 프로세스가 구현되지 않았거나 목적 달성 실패 |
| **1** | Performed | 프로세스가 목적을 달성함 (산출물 존재) |
| **2** | Managed | 계획되고, 모니터링되며, 조정됨 |
| **3** | Established | 표준 프로세스 사용, 조직 전체에 배포됨 |
| **4** | Predictable | 정량적 관리, 통계적으로 제어됨 |
| **5** | Optimizing | 지속적 개선, 근본 원인 분석 |

**현실:** 자동차 업계에서 요구하는 수준은 주로 Level 2~3입니다.
Level 4, 5는 극히 드뭅니다.

---

## 2.2 프로세스 속성 (Process Attributes)

각 레벨은 **프로세스 속성(PA: Process Attribute)**으로 정의됩니다:

| 레벨 | 프로세스 속성 |
|------|-------------|
| Level 1 | PA 1.1 Process Performance |
| Level 2 | PA 2.1 Performance Management, PA 2.2 Work Product Management |
| Level 3 | PA 3.1 Process Definition, PA 3.2 Process Deployment |
| Level 4 | PA 4.1 Quantitative Analysis, PA 4.2 Quantitative Control |
| Level 5 | PA 5.1 Process Innovation, PA 5.2 Process Optimization |

---

## 2.3 평가 등급 (Rating)

각 프로세스 속성은 4등급으로 평가됩니다:

| 등급 | 약어 | 달성 비율 |
|------|------|----------|
| Not Achieved | N | 0~15% |
| Partially Achieved | P | 15~50% |
| Largely Achieved | L | 50~85% |
| Fully Achieved | F | 85~100% |

**레벨 달성 조건:**
- **Level 1 달성:** PA 1.1 = F 또는 L
- **Level 2 달성:** PA 1.1 = F, PA 2.1 = F 또는 L, PA 2.2 = F 또는 L
- **Level 3 달성:** Level 2 달성 + PA 3.1 = F/L, PA 3.2 = F/L

**주의:** 상위 레벨을 달성하려면 하위 레벨의 모든 PA가 F 또는 L이어야 합니다.

# Part 3: 프로세스별 상세 내용

## 3.1 SWE.1 SW Requirements Analysis

### 목적

고객/시스템 요구사항을 소프트웨어 요구사항으로 변환합니다.

### 핵심 기본 실무 (Base Practices)

| BP | 설명 |
|----|------|
| BP1 | 소프트웨어 요구사항 명세 |
| BP2 | 기능적/비기능적 요구사항 구분 |
| BP3 | 요구사항 특성 정의 (우선순위, 출처) |
| BP4 | 요구사항 분석 (실현 가능성, 완전성) |
| BP5 | 인터페이스 요구사항 정의 |
| BP6 | 상위 요구사항과의 추적성 |
| BP7 | 합의 유지 |

### 주요 산출물 (Work Products)

- SW 요구사항 명세서
- 인터페이스 요구사항 문서
- 요구사항 추적 매트릭스 (RTM)
- 분석 보고서

### Level 2에서 추가 확인 (PA 2.2 Work Product Management)

- 산출물이 버전 관리되는가?
- 기준선(Baseline)이 설정되어 있는가?
- 변경 이력이 추적되는가?

---

## 3.2 SWE.4 SW Unit Verification (수환씨 핵심)

### 목적

소프트웨어 단위가 요구사항을 만족하는지 검증합니다.

### 핵심 기본 실무

| BP | 설명 |
|----|------|
| BP1 | 단위 검증 기준 개발 |
| BP2 | 단위 검증 전략 수립 |
| BP3 | 코드 리뷰 수행 |
| BP4 | 정적 분석 수행 |
| BP5 | 단위 테스트 수행 |
| BP6 | 커버리지 달성 확인 (구문, 분기, MC/DC) |
| BP7 | 단위 검증 결과 기록 |

### 자동차 SW에서의 커버리지 요구사항

| ASIL | 요구 커버리지 |
|------|-------------|
| QM | 없음 (권고는 구문) |
| ASIL A | 구문 커버리지 |
| ASIL B | 분기 커버리지 |
| ASIL C | MC/DC |
| ASIL D | MC/DC (필수) |

### 산출물

- 단위 검증 계획서
- 코드 리뷰 결과
- 정적 분석 결과
- 단위 테스트 케이스 및 결과
- 커버리지 보고서

### 목적

소프트웨어 단위를 통합하고 통합된 소프트웨어가 아키텍처 요구사항을 만족하는지 확인합니다.

### 핵심 기본 실무

| BP | 설명 |
|----|------|

| BP3 | 소프트웨어 통합 수행 |
| BP4 | 통합 테스트 수행 |

### 목적

통합된 소프트웨어가 소프트웨어 요구사항을 만족함을 확인합니다.

### 핵심 기본 실무

| BP | 설명 |
|----|------|
| BP1 | 자격 테스트 전략 수립 |
| BP2 | 자격 테스트 명세 개발 |
| BP3 | 자격 테스트 수행 |
| BP4 | 요구사항-테스트 케이스 추적성 확인 |
| BP5 | 결함 보고 및 수정 |
| BP6 | 테스트 완료 보고서 작성 |

### SWE.6 vs SWE.5 차이점

| | SWE.5 | SWE.6 |

| 환경 | 통합 테스트 환경 | 최대한 실제와 유사 |

### 목적

| BP | 설명 |
|----|------|

| BP2 | 문제 식별 및 기록 |

| BP4 | 해결책 개발 및 적용 |

# Part 4: A-SPICE 평가 프로세스

## 4.1 평가 유형

| 유형 | 목적 | 수행자 |
|------|------|--------|
| **자체 평가 (Self-Assessment)** | 내부 개선 목적 | 내부 직원 |
| **1차 평가** | 조직 자체 공식 평가 | 내부 CPA |
| **2차 평가** | OEM이 공급업체 평가 | OEM CPA |
| **3차 평가** | 독립 기관이 평가 | 인증된 외부 CPA |

---

## 4.2 평가 프로세스 단계

### 1단계: 평가 준비

- 평가 범위 결정 (어떤 프로세스를 평가할 것인가)
- 평가 팀 구성
- 피평가 조직에 문서 요청

### 2단계: 문서 검토

- 산출물 검토 (Work Product Review)
- 프로세스 수행 증거 확인
- 프로세스 속성 이행 증거 확인

### 3단계: 인터뷰

- 프로세스 수행 담당자 인터뷰
- 개방형 질문으로 실제 수행 방식 파악

### 4단계: 평가 결과 작성

- 각 PA에 N/P/L/F 등급 부여
- 강점(Strength)과 개선 가능 영역(Improvement Opportunity) 식별

### 5단계: 평가 결과 보고

- 프로세스별 능력 수준 보고
- 개선 권고안 제시

---

## 4.3 평가자 역할

| 역할 | 설명 |
|------|------|
| **Lead Assessor** | 평가 책임자, Intacs CPA 인증 필수 |
| **Competent Assessor** | 능력 있는 평가자 |
| **Observer** | 평가 참관자 (CPA 취득 준비 단계) |

**수환씨의 경로:**
Observer(5일 이상) → 교육 이수 → 필기 시험 → CPA 취득

# Part 5: 추적성 (Traceability)

## 5.1 추적성의 중요성

A-SPICE에서 **추적성(Traceability)**은 Level 1부터 요구되는 핵심 개념입니다.

```
시스템 요구사항
    ↓ 추적
SW 요구사항 (SWE.1)
    ↓ 추적
SW 아키텍처 (SWE.2)
    ↓ 추적
상세 설계 (SWE.3)
    ↓ 추적
단위 테스트 케이스 (SWE.4)
    ↓ 추적
통합 테스트 케이스 (SWE.5)
    ↓ 추적
자격 테스트 케이스 (SWE.6)
```

## 5.2 추적 매트릭스 (Traceability Matrix)

| SW 요구사항 | 테스트 케이스 | 테스트 결과 |
|------------|-------------|-----------|
| REQ-001 | TC-001, TC-002 | PASS |
| REQ-002 | TC-003 | PASS |
| REQ-003 | TC-004, TC-005 | FAIL → 결함 등록 |

PA 3.2(Process Deployment)에 대한 평가는?

a) PA 3.2 = F (프로세스가 있으므로)
b) PA 3.2 = P (일부 프로젝트만 표준 프로세스 적용)
c) PA 3.2 = L (대부분 적용됨)
d) PA 3.2 = N (표준 프로세스 미배포)

**정답: b 또는 d)**
표준 프로세스가 일관되게 배포되지 않으면 PA 3.2 = P 또는 N. 
실제 적용 비율에 따라 다르지만 "각 프로젝트마다 다른"은 배포 실패를 시사합니다.

# 빠른 참조 카드

## SWE 프로세스 암기

```
SWE.1 SW 요구사항 분석
SWE.2 SW 아키텍처 설계
SWE.3 SW 상세 설계 + 단위 구현
SWE.4 SW 단위 검증 (단위 테스트)
SWE.5 SW 통합 + 통합 테스트
SWE.6 SW 자격 테스트
```

## 능력 수준 암기

```
0: Incomplete  - 미구현
1: Performed   - 수행됨 (PA 1.1)
2: Managed     - 계획/모니터링 (PA 2.1, 2.2)
3: Established - 표준화 (PA 3.1, 3.2)
4: Predictable - 정량적 관리 (PA 4.1, 4.2)
5: Optimizing  - 지속 개선 (PA 5.1, 5.2)
```

## 평가 등급 암기

```
N: 0~15%   Not Achieved
P: 15~50%  Partially Achieved
L: 50~85%  Largely Achieved
F: 85~100% Fully Achieved
```

## Level 달성 조건

```
Level 1: PA 1.1 = F/L
Level 2: PA 1.1 = F, PA 2.1 = F/L, PA 2.2 = F/L
Level 3: Level 2 달성 + PA 3.1 = F/L, PA 3.2 = F/L
```

## 수환씨 경험 → CPA 면접 활용

```
SWE.4: IVI 컴포넌트 단위 테스트 수행
SWE.5: IVI ↔ ADAS 통합 테스트 (CAN 통신)
SWE.6: IVI 시스템 자격 테스트 (Regression)
SUP.8: Git 버전 관리, 릴리즈 태그
SUP.9: JIRA 결함 관리, 심각도 분류
추적성: RTM 작성 및 관리
```
