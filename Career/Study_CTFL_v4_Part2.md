# Chapter 4: 테스트 분석 및 설계 (가장 중요, 12문항)

## 4.1 테스트 기법 개요

테스트 기법은 **무엇을 테스트할지, 어떻게 테스트할지** 결정하는 방법입니다.

| 기법 분류 | 기반 | 예시 |
|----------|------|------|
| **블랙박스 (Black-box)** | 명세/요구사항 | EP, BVA, Decision Table, State Transition |
| **화이트박스 (White-box)** | 코드 내부 구조 | Statement, Branch, MC/DC Coverage |
| **경험 기반 (Experience-based)** | 경험과 직관 | Error Guessing, Exploratory Testing |

---

## 4.2 블랙박스 기법 1: 동등값 분할 (Equivalence Partitioning, EP)

### 개념

입력 값의 영역을 **동일하게 처리되는 그룹(파티션)**으로 나눕니다.
같은 파티션 내의 값은 동일하게 처리되므로, 각 파티션에서 **대표값 1개**만 테스트합니다.

**유효 파티션 (Valid Partition):** 시스템이 수용하는 입력
**무효 파티션 (Invalid Partition):** 시스템이 거부해야 하는 입력

### 예시: 나이 입력 (0~120세)

```
무효 파티션  | 유효 파티션 | 무효 파티션
  (음수)    | (0~120)    | (121이상)
   -1       |    60      |    121
```

**테스트 케이스:**
- -1 (무효 파티션) → 오류 메시지 확인
- 60 (유효 파티션) → 정상 처리 확인
- 121 (무효 파티션) → 오류 메시지 확인

### 시험 핵심

- 같은 파티션에서 **1개**만 테스트하면 충분합니다
- 유효/무효 파티션 모두 테스트해야 합니다
- 파티션 수 = 최소 테스트 케이스 수

### 다중 조건 EP

| 조건 | 파티션 |
|------|--------|
| 나이 | 유효(0~120), 무효(<0), 무효(>120) |
| 이름 길이 | 유효(1~50자), 무효(0자), 무효(51자 이상) |

두 조건을 조합할 때는 각 파티션 조합을 테스트합니다.

## 4.3 블랙박스 기법 2: 경계값 분석 (Boundary Value Analysis, BVA)

### 개념

경계 근처에서 결함이 많이 발견됩니다.
경계 값 자체와 경계 바로 위아래 값을 테스트합니다.

### 2-값 BVA (2-value BVA)

경계 값과 바로 인접한 값(경계 ± 1)을 테스트합니다.

```
나이 범위: 0 ~ 120

경계 포인트:
  0의 경계: -1(무효), 0(유효)
  120의 경계: 120(유효), 121(무효)
```

**테스트 케이스:** -1, 0, 120, 121 (총 4개)

### 3-값 BVA (3-value BVA)

경계 값과 양쪽 인접 값 모두 테스트합니다. 더 철저합니다.

```
나이 범위: 0 ~ 120

경계 포인트:
  0의 경계: -1(무효), 0(유효), 1(유효)
  120의 경계: 119(유효), 120(유효), 121(무효)
```

**테스트 케이스:** -1, 0, 1, 119, 120, 121 (총 6개)

### EP vs BVA 비교

| 기법 | 포인트 수 | 목적 |
|------|----------|------|
| EP | 파티션당 1개 | 각 그룹 대표 테스트 |
| 2-값 BVA | 경계당 2개 | 경계 오류 발견 |
| 3-값 BVA | 경계당 3개 | 더 철저한 경계 테스트 |

**시험 함정:** BVA는 EP를 보완합니다. BVA 테스트 케이스는 EP 파티션에도 속합니다.

## 4.4 블랙박스 기법 3: 결정 테이블 (Decision Table Testing)

### 개념

여러 조건의 조합에 따라 다른 동작이 발생하는 경우에 사용합니다.
모든 조건 조합을 체계적으로 표현합니다.

### 구조

```
              규칙1  규칙2  규칙3  규칙4
조건 A         Y      Y      N      N
조건 B         Y      N      Y      N
-----------------------------------------
동작 1 실행    X             X
동작 2 실행           X             X
동작 3 실행    X      X      X      X
```

### 예시: 할인 시스템

조건:
- 회원인가? (Y/N)
- 주문 금액 ≥ 10만원인가? (Y/N)

| | 규칙1 | 규칙2 | 규칙3 | 규칙4 |
|---|---|---|---|---|
| 회원 | Y | Y | N | N |
| 10만원 이상 | Y | N | Y | N |
| **20% 할인** | **X** | | | |
| **10% 할인** | | **X** | **X** | |
| **할인 없음** | | | | **X** |

**테스트 케이스:** 4개의 규칙에 해당하는 입력값 각 1개

### 최소화된 결정 테이블

일부 조건이 동작에 영향을 주지 않으면 테스트 케이스를 통합할 수 있습니다.

**시험 핵심:**
- 조건 수 N → 최대 2^N개 규칙
- 동작이 같으면 조건을 통합(Don't Care)
- 테이블을 완전히 채워야 모든 경우를 커버

## 4.5 블랙박스 기법 4: 상태 전이 테스팅 (State Transition Testing)

### 개념

시스템이 상태를 갖고, 이벤트에 따라 상태가 전이될 때 사용합니다.
상태 다이어그램을 기반으로 테스트 케이스를 설계합니다.

### 구성 요소

| 요소 | 설명 |
|------|------|
| **상태 (State)** | 시스템이 있을 수 있는 조건 |
| **전이 (Transition)** | 한 상태에서 다른 상태로의 변화 |
| **이벤트 (Event)** | 전이를 트리거하는 것 |
| **동작 (Action)** | 전이 중에 발생하는 것 |

### 예시: ATM 카드 잠금 시스템

```
[정상 상태]
    ↓ 비밀번호 오류 1회
[1회 오류]
    ↓ 비밀번호 오류 2회
[2회 오류]
    ↓ 비밀번호 오류 3회
[잠금 상태]
```

**상태 전이 테이블:**

| 현재 상태 | 이벤트 | 다음 상태 | 동작 |
|----------|--------|----------|------|
| 정상 | 비밀번호 정확 | 정상 | 로그인 허용 |
| 정상 | 비밀번호 오류 | 1회 오류 | 경고 1 표시 |
| 1회 오류 | 비밀번호 정확 | 정상 | 로그인 허용 |
| 1회 오류 | 비밀번호 오류 | 2회 오류 | 경고 2 표시 |
| 2회 오류 | 비밀번호 정확 | 정상 | 로그인 허용 |
| 2회 오류 | 비밀번호 오류 | 잠금 | 카드 잠금 |

### 커버리지 기준

| 기준 | 내용 |
|------|------|
| 모든 상태 커버 | 모든 상태를 최소 1번 방문 |
| 모든 전이 커버 | 모든 화살표를 최소 1번 실행 (더 강력) |
| 모든 전이 쌍 커버 | 연속된 전이 쌍 모두 실행 (가장 강력) |

## 4.6 화이트박스 기법 1: 구문 커버리지 (Statement Coverage)

### 개념

코드의 모든 **실행 가능한 구문**을 최소 1번 실행합니다.

### 예시

```python
def classify_age(age):
    if age < 0:              # Line 1
        return "Invalid"     # Line 2
    elif age < 18:           # Line 3
        return "Minor"       # Line 4
    else:
        return "Adult"       # Line 5
```

**100% 구문 커버리지를 위한 최소 테스트:**
- age = -1 → Line 1, 2 실행
- age = 10 → Line 1, 3, 4 실행
- age = 25 → Line 1, 3, 5 실행

**구문 커버리지 계산:**
```
커버된 구문 수 / 전체 구문 수 × 100%
```

**한계:** 모든 구문을 실행해도 모든 분기를 테스트하지는 않습니다.

---

## 4.7 화이트박스 기법 2: 분기 커버리지 (Branch Coverage)

### 개념

코드의 모든 **분기(True/False 경로)**를 최소 1번 실행합니다.
구문 커버리지보다 더 강력합니다.

### 예시

```python
def check_discount(is_member, amount):
    discount = 0
    if is_member:            # 분기 1: True, False
        discount += 10
    if amount >= 100000:     # 분기 2: True, False
        discount += 10
    return discount
```

**100% 분기 커버리지를 위한 테스트:**
- is_member=True, amount=100000 → 분기1=True, 분기2=True
- is_member=False, amount=50000 → 분기1=False, 분기2=False

이 2개의 테스트 케이스로 100% 분기 커버리지 달성.

**중요:** 100% 분기 커버리지 → 100% 구문 커버리지 (반대는 성립하지 않음)

## 4.8 화이트박스 기법 3: MC/DC 커버리지

### 개념

**Modified Condition/Decision Coverage**
항공/자동차 등 안전 필수 시스템에서 요구됩니다 (ISO 26262, DO-178C).

**요구사항:**
1. 모든 조건(Condition)이 True/False를 최소 1번씩 갖는다
2. 각 조건이 독립적으로 결정(Decision)의 결과에 영향을 미침을 보인다

### 예시

```python
if (A and B) or C:   # Decision
    do_something()
```

조건: A, B, C
결정: (A and B) or C

**MC/DC 테스트 케이스:**

| 케이스 | A | B | C | 결과 | 목적 |
|--------|---|---|---|------|------|
| 1 | T | T | F | T | A가 결과를 바꿈 (케이스2와 비교) |
| 2 | F | T | F | F | |
| 3 | T | T | F | T | B가 결과를 바꿈 (케이스4와 비교) |
| 4 | T | F | F | F | |
| 5 | F | F | T | T | C가 결과를 바꿈 (케이스6과 비교) |
| 6 | F | F | F | F | |

**장점:** 분기 커버리지보다 훨씬 철저
**단점:** 테스트 케이스 수가 많음

**자동차 SW와의 관련:**
- ISO 26262 ASIL C/D: MC/DC 커버리지 요구
- CT-AuT 시험에서도 이 개념 출제

## 4.9 경험 기반 기법

### 오류 추측 (Error Guessing)

테스터의 경험을 바탕으로 결함이 있을 것 같은 곳을 테스트합니다.

**자동차 SW에서의 오류 추측 예시:**
- 경계값 근처 (0xFFFF → 오버플로우)
- 타임아웃 처리 (DoIP 응답 없을 때)
- 세션 전환 중 에러 (UDS 세션 전환 타이밍)

### 탐색적 테스팅 (Exploratory Testing)

테스트를 **계획, 설계, 실행**을 동시에 진행합니다.
스크립트 없이 테스터가 자유롭게 탐색합니다.

**특징:**
- 사전 스크립트 없음
- 새로운 발견에 따라 방향 전환
- 세션 기반 관리 (타임박스)
- 공식 테스트가 놓친 결함 발견에 효과적

**시험 함정:** 탐색적 테스팅은 "계획 없는 테스팅"이 아닙니다.
목적과 범위는 있고, 사전 스크립트가 없는 것입니다.

### 체크리스트 기반 테스팅 (Checklist-based Testing)

경험에서 나온 체크리스트를 기반으로 테스팅합니다.
일관성과 반복성이 보장됩니다.

# Chapter 5: 테스트 관리 (Test Management)

## 5.1 테스트 계획 (Test Planning)

### 테스트 계획서 내용

| 항목 | 설명 |
|------|------|
| 범위 (Scope) | 무엇을 테스트하는가 / 하지 않는가 |
| 목적 (Objectives) | 테스팅의 목표 |
| 접근법 (Approach) | 어떤 기법, 도구 사용할 것인가 |
| 자원 (Resources) | 팀, 환경, 도구 |
| 일정 (Schedule) | 테스팅 활동의 타임라인 |
| 리스크 (Risks) | 테스팅에 영향을 주는 리스크 |
| 완료 기준 (Exit Criteria) | 테스팅을 언제 멈출 것인가 |

### 진입 기준 vs 완료 기준

| 기준 | 의미 | 예시 |
|------|------|------|
| **진입 기준 (Entry Criteria)** | 테스팅을 시작하기 위한 조건 | 테스트 환경 준비, 요구사항 승인 |
| **완료 기준 (Exit Criteria)** | 테스팅을 완료하기 위한 조건 | 95% 테스트 케이스 실행, 치명적 결함 0개 |

## 5.1.2 테스트 노력 추정 (Test Effort Estimation)

> **v4.0 신규 출제 영역** — K3 수준 (적용 가능해야 함)

테스트에 필요한 시간과 자원을 예측하는 기법들입니다.

### 기반 기법 비교 (시험 필수)

| 기법 | 기반 | 장점 | 단점 |
|------|------|------|------|
| **전문가 기반** | 경험, 직관 | 빠름 | 주관적, 검증 어려움 |
| **유추 기반** | 과거 유사 프로젝트 | 현실적 | 과거 데이터 필요 |
| **Wideband Delphi** | 전문가 집단 합의 | 객관적, 편향 줄임 | 시간 소요 |
| **기능 점수** | 기능 복잡도 | 표준화됨 | 전문 지식 필요 |

### Wideband Delphi — 가장 중요한 추정 기법

v4.0에서 명시적으로 추가된 추정 기법입니다.

**진행 방식:**

```
1단계: 브리핑
  → 조정자(Moderator)가 프로젝트 정보를 전문가들에게 설명

2단계: 개별 추정
  → 각 전문가가 독립적으로(서로 보지 않고) 노력 추정치 작성

3단계: 결과 공개
  → 모든 추정치를 동시에 공개 (서로 영향을 주지 않도록)

4단계: 토론
  → 추정치 차이가 큰 경우 토론 → 이유 공유

5단계: 재추정
  → 토론 후 다시 개별 추정
  → 수렴할 때까지 2~5단계 반복

6단계: 합의
  → 최종 추정치 도출
```

**핵심 특징:**
- **익명성**: 다른 전문가 의견에 영향받지 않음 (편향 방지)
- **반복**: 합의에 도달할 때까지 반복
- **집단 지성**: 한 사람보다 여러 전문가 의견이 더 정확

**시험 함정:** Wideband Delphi에서 중요한 것은 **개별 추정을 동시에 공개**하는 것입니다. 순서대로 발표하면 앞 사람 의견에 편향됩니다.

**Planning Poker와의 관계:**
- Planning Poker는 Wideband Delphi를 애자일에 적용한 변형
- 카드로 추정치를 동시에 공개 → 같은 원리

### 테스트 추정에 영향을 주는 요인

**제품 특성:**
- 코드 크기와 복잡도
- 요구사항 안정성 (자주 바뀌면 추정 어려움)
- 품질 요구 수준 (항공/자동차 ASIL D > 일반 앱)

**프로세스 특성:**
- 테스트 프로세스 성숙도
- 자동화 수준 (높을수록 재실행 비용 절감)
- 도구 지원 수준

**팀 특성:**
- 도메인 경험 (자동차 SW vs 모바일 앱)
- 기술 역량
- 팀 크기

---

## 5.2 리스크 기반 테스팅 (Risk-based Testing)

### 리스크란

**가능성 × 영향도 = 리스크 수준**

테스팅 자원이 한정되어 있으므로,
리스크가 높은 영역을 먼저, 더 많이 테스트합니다.

### 제품 리스크 vs 프로젝트 리스크

| 유형 | 정의 | 예시 |
|------|------|------|
| **제품 리스크** | 소프트웨어 품질과 관련된 리스크 | 브레이크 시스템 결함 |
| **프로젝트 리스크** | 프로젝트 관리와 관련된 리스크 | 일정 지연, 자원 부족 |

**시험 핵심:**
- 리스크 기반 테스팅은 제품 리스크를 우선순위화합니다
- 리스크가 높으면 더 많은 테스트를 수행합니다

---

## 5.3 테스트 모니터링, 제어, 완료

### 테스트 진행 보고 지표

| 지표 | 의미 |
|------|------|
| 테스트 케이스 실행율 | 전체 중 실행된 TC 비율 |
| 합격/불합격 비율 | 통과/실패 TC 비율 |
| 결함 발견율 | 시간당 새로운 결함 수 |
| 결함 해결율 | 발견된 결함 중 수정된 비율 |

### 테스트 완료 보고서 내용

- 테스팅 목표 달성 여부
- 발견된 결함 요약
- 미완료 테스트 케이스
- 잔존 리스크
- 교훈 (Lessons Learned)

## 5.4 결함 관리 (Defect Management)

### 결함 보고서 필수 항목

| 항목 | 설명 |
|------|------|
| 고유 식별자 (ID) | 결함 추적을 위한 번호 |
| 제목 | 결함의 간략한 설명 |
| 재현 단계 | 결함을 재현하는 방법 |
| 실제 결과 | 실제로 무슨 일이 일어났는가 |
| 기대 결과 | 무슨 일이 일어나야 했는가 |
| 심각도 (Severity) | 비즈니스에 미치는 영향 |
| 우선순위 (Priority) | 수정의 시급성 |
| 상태 | 신규/오픈/수정됨/닫힘 등 |

### 심각도 vs 우선순위 구분 (시험 핵심)

| 구분 | 정의 | 예시 |
|------|------|------|
| **심각도 (Severity)** | 결함이 시스템에 미치는 영향 | 시스템 크래시 = Critical |
| **우선순위 (Priority)** | 수정해야 하는 시급성 | 회장 이름 오타 = High Priority but Low Severity |

**예시:**
- 회장 이름 오타 → 심각도: 낮음, 우선순위: 높음 (PR 문제)
- 메모리 누수 → 심각도: 높음, 우선순위: 낮음 (서비스에 즉각 영향 없음)

## 6.2 테스트 자동화 (Test Automation)

### 이점

- 반복 테스트의 빠른 실행
- 회귀 테스팅 효율 향상
- 일관성 (사람의 실수 제거)
- 야간/주말 실행 가능

### 위험과 한계

- 초기 구현 비용 높음
- 유지보수 필요 (소프트웨어 변경 시 테스트도 변경)
- 모든 테스트를 자동화할 수 없음 (탐색적, 사용성 등)
- 자동화가 항상 더 좋은 것은 아님

### 자동화 실패 원인

- 과도한 자동화 기대
- 품질이 낮은 소프트웨어에 자동화 적용
- 유지보수 비용 과소 평가
- 적절한 훈련 없이 도구 도입

---

## 6.3 테스트 자동화의 적합한 대상

**자동화에 적합:**
- 회귀 테스팅
- 반복적 데이터 입력 테스트
- 성능/부하 테스팅
- 스모크 테스팅

**자동화에 부적합:**
- 탐색적 테스팅
- 사용성 테스팅
- 일회성 테스트
- 자주 변경되는 기능

# 빠른 참조 카드 (Quick Reference Card)

## 7가지 테스팅 원칙 암기

```
1. 결함 존재 보여줌 (결함 없음 증명 불가)
2. 완전한 테스팅 불가능
3. 조기 테스팅 (Shift-Left)
4. 결함 집중 (20% 모듈에 80% 결함)
5. 살충제 역설 (같은 TC 반복 → TC 갱신 필요)
6. 맥락 의존성 (소프트웨어 유형마다 다름)
7. 결함 부재의 오류 (결함 없어도 실패 가능)
```

## Error → Defect → Failure 연쇄

```
Error (사람의 실수)
  ↓ 코드에 반영
Defect (코드/문서의 결함)
  ↓ 해당 코드 실행 시
Failure (시스템 장애)
```

## 테스트 레벨 요약 (v4.0 — 5개 레벨)

```
컴포넌트 테스팅      → 개발자가 단위 테스트 (단위 레벨)
컴포넌트 통합 테스팅  → 소프트웨어 컴포넌트 간 인터페이스
시스템 테스팅        → 독립 팀, 완전한 시스템
시스템 통합 테스팅    → 시스템 간 인터페이스 ★v4.0 신규★
인수 테스팅          → 사용자/고객이 수용 결정
```

## 블랙박스 기법 요약

```
EP (동등값 분할):
  파티션당 대표값 1개, 유효+무효 모두 테스트

BVA 2-값:
  경계값 + 경계±1 → 경계당 2개

BVA 3-값:
  경계값 + 양쪽 인접값 → 경계당 3개

결정 테이블:
  조건 N개 → 최대 2^N 규칙
  Don't Care로 규칙 통합 가능

상태 전이:
  상태/전이/이벤트/동작
  커버리지: 상태 < 전이 < 전이 쌍
```

## 화이트박스 기법 요약

```
구문 커버리지: 모든 구문 1회 실행
  → 가장 약한 기준

분기 커버리지: 모든 True/False 경로
  → 100% 분기 = 100% 구문 (역은 성립 안 함)

MC/DC 커버리지:
  → 각 조건이 독립적으로 결정에 영향
  → 안전 필수 시스템 요구 (ISO 26262, DO-178C)
```

## 리뷰 유형 비교

```
비공식 리뷰: 프로세스 없음, 빠른 피드백
워크스루: 작성자가 진행, 토론 중심
기술 리뷰: 기술 전문가, 표준 확인
인스펙션: 가장 공식, 역할 분리 명확
           계획→킥오프→개별준비→리뷰→수정→완료
```

## 심각도 vs 우선순위

```
심각도 (Severity): 시스템에 미치는 영향
우선순위 (Priority): 수정의 시급성

예: CEO 이름 오타
  심각도: 낮음 (기능 영향 없음)
  우선순위: 높음 (PR 문제, 즉시 수정)
```

## v4.0 신규 핵심 암기 ★

```
테스트 우선 접근법:
  TDD  → 개발자, 단위 레벨, Red-Green-Refactor
  ATDD → 전체 팀, 인수 레벨, 인수 기준 먼저
  BDD  → 전체 팀, Given/When/Then, 자연어

테스트 피라미드 (하단→상단):
  단위 테스트: 많이, 빠름, 저렴
  통합 테스트: 중간
  UI/E2E:     적게, 느림, 비쌈

테스팅 사분면:
  Q1 (기술/개발지원): 단위, 컴포넌트 (자동화)
  Q2 (비즈니스/개발지원): 기능, 인수 (자동화+수동)
  Q3 (비즈니스/제품비판): 탐색적, 사용성 (수동)
  Q4 (기술/제품비판): 성능, 보안 (도구)

Wideband Delphi:
  독립 추정 → 동시 공개 → 토론 → 재추정 → 합의
  Planning Poker = Wideband Delphi의 애자일 버전

Shift-Left: 테스팅을 일찍 시작 (빨리 끝내는 것 아님)
DevOps: CI/CD 파이프라인에서 자동화 피드백
회고: 스프린트 종료 후 테스트 프로세스 개선
```

## 자동화 적합 vs 부적합

```
적합: 회귀 테스팅, 성능 테스팅, 반복 데이터 입력
부적합: 탐색적, 사용성, 일회성, 자주 변경되는 기능
```

## 자동차 SW 연계 포인트 (CT-AuT 준비)

```
UDS 세션 전환 → 상태 전이 테스팅
DoIP 타임아웃 → 경계값 분석 + 상태 전이
IVI 기능 조합 → 결정 테이블
브레이크 제어 → MC/DC 커버리지 (ISO 26262)
OTA 업데이트 후 → 확인 테스팅 + 회귀 테스팅
```
