# Chapter 1: 테스팅의 기초 (Fundamentals of Testing)

## 1.1 테스팅이란 무엇인가

### 테스팅의 정의

테스팅은 소프트웨어 제품과 관련 작업 산출물을 **평가**하여 요구사항을 충족하는지,
목적에 적합한지, 결함을 찾아내기 위한 **활동들의 집합**입니다.

**중요: 테스팅 ≠ 실행만**
테스팅에는 계획, 분석, 설계, 실행, 보고가 모두 포함됩니다.
코드를 실행하는 것은 테스팅의 일부에 불과합니다.

### 테스팅의 목적 (K1 — 암기 필수)

시험에 자주 나오는 목적 목록:

1. **결함 예방** — 테스팅 활동 자체가 결함을 줄인다
2. **요구사항 검증** — 명세한 대로 만들어졌는지 확인
3. **검증** — 사용자 요구에 맞는지 확인
4. **의사결정 지원** — 릴리즈 여부 판단 정보 제공
5. **신뢰 구축** — 품질에 대한 신뢰 증가
6. **법적/규제 준수** — 계약, 표준, 규제 요건 충족
7. **결함 발견** — 실패 원인인 결함을 발견

**시험 함정:** "테스팅의 목적은 소프트웨어가 결함이 없음을 증명하는 것이다" → **틀림**
테스팅은 결함이 없음을 증명할 수 없습니다. 결함을 찾는 것입니다.

---

## 1.2 테스팅이 왜 필요한가

### 소프트웨어 실패의 원인 연쇄

```
사람의 실수 (Error/Mistake)
        ↓ 코드에 반영되면
결함 (Defect/Bug/Fault)
        ↓ 실행 시 발생하면
장애 (Failure)
```

**용어 구분 (시험에 자주 출제):**

| 용어 | 정의 | 예시 |
|------|------|------|
| **Error (실수)** | 사람이 잘못된 결과를 낸 행동 | 개발자가 조건을 거꾸로 씀 |
| **Defect (결함)** | 코드/문서에 존재하는 결함 | `if x > 0`이어야 하는데 `if x < 0` |
| **Failure (장애)** | 시스템이 요구 동작과 다르게 동작 | 음수 입력 시 오류 발생 |

**중요:** 결함이 항상 장애로 이어지지는 않습니다.
- 사용되지 않는 코드의 결함 → 장애 없음
- 결함이 특정 조건에서만 발생 → 항상 장애 아님

### 테스팅의 기여

- **조기 테스팅**: 초기에 발견한 결함이 나중에 발견한 것보다 수정 비용이 훨씬 낮음
- **비용 곡선**: 설계 단계 결함 수정 < 개발 단계 수정 < 출시 후 수정

## 1.3 테스팅 원칙 (7가지 — 가장 중요한 암기 항목)

**시험에서 3~4문항 출제. 전부 암기하세요.**

### 원칙 1: 테스팅은 결함의 존재를 보여주지, 결함 부재를 보여주지 않는다

테스팅은 결함이 있음을 보여줄 수 있지만,
결함이 없다는 것을 증명할 수는 없습니다.

**시험 함정:** "충분한 테스팅을 수행하면 소프트웨어에 결함이 없음을 보장할 수 있다" → **거짓**

### 원칙 2: 완전한 테스팅은 불가능하다

입력 값, 경로, 조건의 모든 조합을 테스트하는 것은 불가능합니다.
리스크와 우선순위에 따라 테스트 범위를 집중해야 합니다.

**예외처럼 보이지만 아닌 것:**
"아주 작은 프로그램은 모든 경우를 테스트할 수 있지 않나?" →
이론적으로는 그렇지만, 실제 시스템에서는 불가능합니다.

### 원칙 3: 조기 테스팅은 시간과 비용을 절약한다

가능한 한 일찍 테스팅을 시작하면 결함을 조기에 발견하여 수정 비용을 낮춥니다.
이것을 **Shift-Left**라고 합니다.

### 원칙 4: 결함 집중 (Defect Clustering)

결함은 소수의 컴포넌트에 집중되는 경향이 있습니다.
일반적으로 80%의 결함이 20%의 모듈에서 발견됩니다 (파레토 법칙).

**적용:** 결함이 많이 발견된 모듈에 테스트를 집중하는 것이 효율적입니다.

### 원칙 5: 살충제 역설 (Pesticide Paradox)

같은 테스트를 반복하면 새로운 결함을 발견하지 못합니다.
테스트 케이스를 정기적으로 검토하고 수정해야 합니다.

**시험 함정:** "같은 테스트 케이스를 반복 실행하면 점점 더 많은 결함을 찾는다" → **거짓**

### 원칙 6: 테스팅은 맥락에 의존한다

테스팅 방법은 소프트웨어 유형에 따라 다릅니다.
의료 소프트웨어 테스팅 ≠ 게임 앱 테스팅 ≠ 자동차 제어 소프트웨어 테스팅

### 원칙 7: 결함 부재의 오류 (Absence of Defects Fallacy)

결함이 없다고 해서 소프트웨어가 성공한 것은 아닙니다.
사용자의 필요와 기대를 충족하지 못한다면 의미가 없습니다.

**예시:** 결함이 없지만 사용자가 원하지 않는 기능을 구현한 소프트웨어

## 1.4 테스트 프로세스 (Test Process)

### 테스트 활동과 태스크

CTFL v4.0에서는 테스트 프로세스를 다음과 같이 정의합니다:

#### 1) 테스트 계획 (Test Planning)
- 테스팅 범위, 목표, 리스크, 접근 방법 정의
- 테스트 일정, 자원, 비용 계획
- **산출물:** 테스트 계획서

#### 2) 테스트 모니터링 및 제어 (Test Monitoring and Control)
- 진행 상황 모니터링 (계획 대비 실제)
- 편차 발생 시 수정 조치

#### 3) 테스트 분석 (Test Analysis)
- 테스트 베이시스 분석 (요구사항, 설계 등)
- 테스트 조건 (Test Condition) 식별
- **"무엇을 테스트할 것인가"**를 결정

#### 4) 테스트 설계 (Test Design)
- 테스트 케이스 설계
- 테스트 데이터 식별
- **"어떻게 테스트할 것인가"**를 결정

#### 5) 테스트 구현 (Test Implementation)
- 테스트 프로시저 생성
- 테스트 스위트 구성
- 테스트 환경 준비

#### 6) 테스트 실행 (Test Execution)
- 테스트 케이스 실행
- 실제 결과와 기대 결과 비교
- 결함 기록

#### 7) 테스트 완료 (Test Completion)
- 테스트 완료 보고서 작성
- 테스트웨어 아카이빙
- 교훈 정리

## 1.5 테스트 베이시스와 테스트 오라클

### 테스트 베이시스 (Test Basis)

테스트 케이스 설계의 기반이 되는 문서/정보:
- 요구사항 명세서
- 설계 문서
- 소스 코드
- 사용자 매뉴얼
- 인터뷰, 경험 등

### 테스트 오라클 (Test Oracle)

실제 결과가 맞는지 틀린지 판단하는 기준:
- 요구사항 문서
- 참조 시스템 (이전 버전)
- 사용자 기대
- 전문가 판단

**중요:** 테스트 오라클 문제(Test Oracle Problem) = 실제로 옳은 결과가 무엇인지 모를 때 발생

## 1.6 테스터와 개발자의 심리

### 개발자 vs 테스터 사고방식

| 개발자 | 테스터 |
|--------|--------|
| 코드가 동작하길 원함 | 코드가 실패하길 원함 (결함 발견) |
| 만드는 사람 | 평가하는 사람 |
| 확인 편향 있음 | 비판적 사고 필요 |

### 독립적 테스팅의 이점

개발자가 자신의 코드를 직접 테스트하면 확인 편향 때문에 결함을 놓칩니다.
독립적인 테스터가 더 많은 결함을 발견하는 이유입니다.

**독립성 수준 (낮음 → 높음):**
1. 개발자 자신이 테스트
2. 같은 팀의 다른 개발자
3. 별도 테스트 팀 (같은 조직)
4. 외부 테스트 전문 기관

# Chapter 2: SDLC와 테스팅

## 2.1 소프트웨어 개발 수명주기 모델

### 순차적 개발 모델 — 워터폴

```
요구사항 → 설계 → 구현 → 검증 → 운영/유지보수
```

**특징:**
- 단계가 완료되어야 다음 단계로 넘어감
- 변경 대응이 어렵고 비쌈
- 후반에 테스팅 집중 → 결함 발견 늦음

**테스팅 적용:** 모든 개발 완료 후 테스팅 시작

### V-모델 (순차적 + 테스팅 강조)

```
요구사항 분석 ←→ 인수 테스팅
    시스템 설계 ←→ 시스템 테스팅
      컴포넌트 설계 ←→ 통합 테스팅
         코딩 ←→ 컴포넌트 테스팅
```

**핵심:** 각 개발 단계에 대응하는 테스트 레벨이 있습니다.
개발 단계에서 테스트 계획을 미리 수립합니다.

### 반복적/점진적 개발 모델

**반복적 (Iterative):** 기능을 반복하면서 점점 완성
**점진적 (Incremental):** 기능을 조금씩 추가하며 완성

**예시:** Rational Unified Process (RUP), Scrum, Kanban

### 애자일 (Agile)

| 항목 | 내용 |
|------|------|
| 스프린트 | 1~4주 반복 주기 |
| 테스팅 | 스프린트 내에서 지속적으로 수행 |
| 특징 | 문서보다 소프트웨어, 계획보다 적응 |
| 테스터 역할 | 팀의 일원, 스프린트 내 테스팅 |

## 2.2 테스트 레벨 (Test Levels)

### 컴포넌트 테스팅 (Component Testing / Unit Testing)

| 항목 | 내용 |
|------|------|
| 대상 | 개별 컴포넌트 (함수, 클래스, 모듈) |
| 담당 | 주로 개발자 |
| 기반 | 컴포넌트 명세, 소스 코드 |
| 특징 | 스텁(Stub), 드라이버(Driver) 사용 |

**스텁 vs 드라이버:**
- **스텁 (Stub):** 아직 개발되지 않은 하위 컴포넌트를 대체하는 더미
- **드라이버 (Driver):** 테스트 대상 컴포넌트를 호출하는 상위 컴포넌트를 대체

### 통합 테스팅 (Integration Testing)

| 항목 | 내용 |
|------|------|
| 대상 | 컴포넌트 간 인터페이스와 상호작용 |
| 담당 | 개발자 또는 테스터 |
| 집중 | 컴포넌트들이 함께 잘 동작하는가 |

**통합 순서:**
- **빅뱅 (Big Bang):** 한꺼번에 통합 → 결함 위치 특정 어려움
- **점진적:** 하향식 (Top-Down) 또는 상향식 (Bottom-Up)

### 시스템 테스팅 (System Testing)

| 항목 | 내용 |
|------|------|
| 대상 | 완전한 시스템 |
| 담당 | 독립적인 테스트 팀 |
| 환경 | 가능한 한 실제 환경과 유사하게 |
| 기반 | 시스템 요구사항, 리스크 |

### 인수 테스팅 (Acceptance Testing)

| 항목 | 내용 |
|------|------|
| 대상 | 시스템이 사용자/비즈니스 요구를 충족하는가 |
| 담당 | 사용자, 고객, 비즈니스 대표 |
| 유형 | UAT, 운영 인수, 계약 인수, 규제 인수, 알파/베타 |

## 2.3 테스트 유형 (Test Types)

### 기능 테스팅 (Functional Testing)

**"시스템이 무엇을 해야 하는가"**를 검증
- 기능적 요구사항 테스팅
- 블랙박스 테스팅이 주로 사용됨

### 비기능 테스팅 (Non-Functional Testing)

**"시스템이 얼마나 잘 동작하는가"**를 검증

| 비기능 특성 | 예시 |
|------------|------|
| 성능 | 응답 시간, 처리량 |
| 보안 | 권한 없는 접근 방지 |
| 호환성 | 다른 OS/브라우저에서 동작 |
| 사용성 | 사용하기 쉬운가 |
| 신뢰성 | 오랫동안 안정적으로 동작 |
| 유지보수성 | 변경이 쉬운가 |

### 화이트박스 테스팅 (White-box / Structural Testing)

코드 내부 구조를 기반으로 테스트 케이스를 설계합니다.
내부 구현에 접근 가능해야 합니다.

### 변경 관련 테스팅

**확인 테스팅 (Confirmation Testing):**
발견된 결함이 수정되었는지 확인하는 테스팅

**회귀 테스팅 (Regression Testing):**
변경이 이전에 잘 동작하던 기능을 망가뜨리지 않았는지 확인

**시험 함정:** 결함 수정 후 처음 하는 것은 **확인 테스팅**,
그 다음에 다른 기능에 영향을 주지 않았는지 **회귀 테스팅**을 합니다.

## 2.4 유지보수 테스팅 (Maintenance Testing)

이미 출시된 소프트웨어를 변경할 때의 테스팅.

**변경 유형:**
- 적응적 변경 (환경 변화 대응)
- 수정적 변경 (결함 수정)
- 향상적 변경 (기능 추가)

**테스팅 범위 결정 요소:**
- 변경의 리스크 크기
- 기존 시스템의 크기
- 변경된 부분의 크기

## 2.5 CTFL v4.0 신규 내용 — 개발 방식과 테스팅

> **시험 출제 비중 높음** — v4.0에서 새로 추가된 내용으로 v3.1 기반 교재에는 없습니다.

### 시스템 통합 테스팅 (System Integration Testing) — 5번째 테스트 레벨

CTFL v4.0에서 **새로 추가된 테스트 레벨**입니다.

| 레벨 | 이름 | 대상 |
|------|------|------|
| 1 | 컴포넌트 테스팅 | 개별 단위 |
| 2 | 컴포넌트 통합 테스팅 | 컴포넌트 간 인터페이스 |
| 3 | 시스템 테스팅 | 전체 시스템 |
| **4** | **시스템 통합 테스팅** | **시스템 간 인터페이스 (v4.0 신규)** |
| 5 | 인수 테스팅 | 사용자/비즈니스 요구사항 |

**시스템 통합 테스팅이란:**
- 여러 시스템(자체 시스템 + 외부 시스템 + API)을 통합했을 때의 인터페이스 검증
- 예: IVI ↔ ADAS ↔ 클라우드 백엔드 전체 연동 테스팅

**컴포넌트 통합 테스팅 vs 시스템 통합 테스팅:**

| | 컴포넌트 통합 테스팅 | 시스템 통합 테스팅 |
|-|---------------------|------------------|
| 대상 | 소프트웨어 컴포넌트 간 | 시스템 간 (외부 포함) |
| 환경 | 개발 환경 | 실제 또는 유사 환경 |
| 담당 | 개발자/테스터 | 독립 테스트 팀 |

**시험 함정:** "시스템 통합 테스팅"은 시스템 간 인터페이스를 테스트하는 것이지, 시스템 내부 통합이 아닙니다.

---

### 테스트 우선 접근법 (Test-First Approaches)

v4.0에서 새로 추가된 개발-테스팅 통합 방법들입니다.

#### TDD (Test-Driven Development) — 테스트 주도 개발

```
1. 실패하는 단위 테스트 작성 (Red)
2. 테스트를 통과하는 최소한의 코드 작성 (Green)
3. 코드 리팩토링 (Refactor)
   → 반복
```

**특징:**
- 개발자가 수행
- 단위/컴포넌트 레벨
- 코드 품질 향상 + 자동화된 회귀 테스트 세트 생성
- "테스트가 설계를 유도한다"

#### ATDD (Acceptance Test-Driven Development) — 인수 테스트 주도 개발

```
1. 팀 전체가 인수 기준 협의 (개발자 + 테스터 + 비즈니스)
2. 인수 테스트 케이스 작성 (실패)
3. 기능 구현
4. 인수 테스트 통과
```

**특징:**
- 팀 전체 참여 (Three Amigos: 개발자, 테스터, 비즈니스 분석가)
- 인수 레벨
- 공유된 이해 확보

#### BDD (Behavior-Driven Development) — 행동 주도 개발

**Gherkin 문법으로 시나리오 작성:**

```gherkin
Feature: 로그인
  Scenario: 유효한 자격증명으로 로그인
    Given 사용자가 로그인 페이지에 있다
    When 올바른 아이디와 비밀번호를 입력한다
    Then 대시보드 화면으로 이동한다
```

**특징:**
- 비기술적 이해관계자도 이해 가능한 자연어 사용
- Given/When/Then 구조
- Cucumber, SpecFlow 등 도구 사용

**TDD/ATDD/BDD 비교:**

| 방식 | 수행자 | 레벨 | 언어 |
|------|--------|------|------|
| TDD | 개발자 | 단위 | 코드 |
| ATDD | 전체 팀 | 인수 | 비즈니스 언어 |
| BDD | 전체 팀 | 인수/시스템 | 자연어(Gherkin) |

**공통점:** 모두 테스트를 먼저 작성하여 구현을 유도합니다.

---

### Shift-Left 테스팅 (조기 테스팅)

v4.0에서 원칙 3(조기 테스팅)이 Shift-Left로 명시적으로 연결됩니다.

**Shift-Left의 의미:**
- 테스팅 활동을 개발 라이프사이클의 **왼쪽(초기)**으로 이동
- 요구사항 단계부터 테스트 관점으로 검토

**구체적 실천 방법:**
- 요구사항 리뷰에 테스터 참여
- 정적 분석 도구를 CI 파이프라인에 통합
- TDD/ATDD/BDD 적용
- 테스트 설계를 구현과 병행

**비용 이점:**
```
요구사항 단계 결함 수정 비용 = 1x
설계 단계                  = 3x
구현 단계                  = 10x
테스트 단계                = 40x
출시 후                    = 100x+
```

**시험 함정:** Shift-Left는 테스팅을 빨리 끝내는 것이 아니라, **일찍 시작**하는 것입니다.

---

### 테스트 피라미드 (Test Pyramid)

마이크 코인이 제안한 자동화 테스트 구조 모델.

```
        /\
       /UI\          ← 적게 (느리고 비쌈)
      /----\
     /통합  \         ← 적당히
    /--------\
   /  단위    \       ← 많이 (빠르고 저렴)
  /____________\
```

**각 레이어:**

| 레이어 | 특징 | 비중 |
|--------|------|------|
| **단위 테스트** | 빠름, 저렴, 격리됨 | 가장 많이 |
| **통합 테스트** | 인터페이스 검증 | 중간 |
| **UI/E2E 테스트** | 느림, 비쌈, 취약함 | 가장 적게 |

**테스트 피라미드의 교훈:**
- 하위 레벨에서 더 많은 결함을 일찍 발견하라
- UI 테스트에 너무 의존하면 "아이스크림 콘" 안티패턴
- 자동화 우선 순위: 단위 > 통합 > UI

**시험 핵심:** 피라미드 하단일수록 더 많이, 빠르게, 저렴하게 테스트 가능합니다.

---

### 테스팅 사분면 (Testing Quadrants)

브라이언 마릭의 모델. 테스트 활동을 두 축으로 분류합니다.

```
       지원하는(Supporting)        비즈니스 직면(Business Facing)
            ↑
  Q2         |          Q1
  인수 테스팅  |  기능 테스팅
  시나리오 테스팅|  스토리 테스팅
  사용자 테스팅  |  프로토타입
             |
  -----------+-----------
             |
  Q3         |          Q4
  탐색적 테스팅|  성능 테스팅
  사용성 테스팅 |  보안 테스팅
  알파/베타   |  부하 테스팅
             |
        기술 직면(Technology Facing)
```

| 사분면 | 목적 | 지원 대상 |
|--------|------|----------|
| **Q1 (자동화)** | 단위·통합 테스트 | 팀 (기술적, 개발 지원) |
| **Q2 (자동화+수동)** | 기능·인수 테스트 | 제품 (비즈니스, 개발 지원) |
| **Q3 (수동)** | 탐색적·사용성 | 제품 (비즈니스, 제품 비판) |
| **Q4 (도구)** | 성능·보안 | 팀 (기술적, 제품 비판) |

**시험 핵심:** 사분면은 테스트를 누락 없이 계획하기 위한 모델입니다.

### 회고 (Retrospectives)와 테스트 개선

애자일에서 스프린트 종료 후 수행하는 **회고**는 테스트 프로세스 개선에도 활용됩니다.

**회고에서 논의할 테스팅 관련 항목:**
- 어떤 테스트 기법이 효과적이었나?
- 결함이 예상보다 늦게 발견된 이유는?
- 자동화 범위를 넓힐 수 있는가?
- 테스트 환경 문제는 없었나?

**회고를 통한 개선 사이클:**
```
테스트 실행 → 결과 분석 → 회고 → 개선 계획 → 적용 → 반복
```

### DevOps와 테스팅

DevOps(개발+운영 통합)는 테스팅 방식에 큰 변화를 가져옵니다.

**CI/CD 파이프라인에서의 테스팅:**

```
코드 커밋
    ↓
정적 분석 (자동)
    ↓
단위 테스트 (자동)
    ↓
통합 테스트 (자동)
    ↓
배포 (스테이징)
    ↓
인수 테스트 (자동/수동)
    ↓
배포 (프로덕션)
    ↓
모니터링 (자동)
```

**DevOps에서 테스터의 역할 변화:**
- 수동 실행자 → 자동화 설계자
- 별도 단계 → 파이프라인 통합
- 버그 발견 → 품질 내재화 (Quality Built-in)

**장점:**
- 빠른 피드백 (커밋 후 수분 내)
- 지속적 품질 확인
- 회귀 테스트 자동 실행

## 2.6 전체 팀 접근법 (Whole Team Approach)

애자일에서 테스팅은 **전체 팀의 책임**입니다.

**전통적 테스팅 vs 전체 팀 접근법:**

| | 전통적 | 전체 팀 접근법 |
|-|--------|-------------|
| 테스팅 책임 | 테스트 팀만 | 팀 전체 |
| 테스터 역할 | 독립적 검증 | 개발자와 협업 |
| 결함 발견 시점 | 개발 후 | 지속적으로 |
| 품질 책임 | QA 팀 | 모든 팀원 |

**실천 방법:**
- 개발자도 자신의 코드를 단위 테스트
- 테스터가 요구사항 분석에 참여
- 비즈니스 담당자가 인수 기준 정의
- 모두가 코드 리뷰에 참여

# Chapter 3: 정적 테스팅 (Static Testing)

## 3.1 정적 테스팅 기초

### 정적 vs 동적 테스팅

| 구분 | 정적 테스팅 | 동적 테스팅 |
|------|-----------|-----------|
| 코드 실행 | **실행하지 않음** | 실행함 |
| 대상 | 문서, 코드, 설계 등 모든 작업 산출물 | 실행 가능한 소프트웨어 |
| 목적 | 결함, 개선 가능 영역, 불일치 발견 | 장애 발생 확인 |
| 예시 | 리뷰, 정적 분석 도구 | 단위 테스트, 시스템 테스트 |

**핵심 차이:** 정적 테스팅은 소프트웨어를 **실행하지 않고** 결함을 찾습니다.

### 정적 테스팅으로 발견 가능한 결함 예시

- 요구사항의 모순, 불명확성
- 설계 결함 (잘못된 알고리즘, 불필요한 복잡성)
- 코딩 표준 위반
- 보안 취약점 (SQL 인젝션 가능성 등)
- 테스트 케이스의 누락이나 오류
- 문서화 오류

---

## 3.2 피드백과 리뷰 프로세스

### 리뷰의 이점

- 개발 초기에 결함 발견 → 수정 비용 절감
- 공유된 이해로 커뮤니케이션 개선
- 표준 준수 확인

### 리뷰 유형

#### 비공식 리뷰 (Informal Review)

- 공식 프로세스 없음
- 동료 검토, 짝 프로그래밍 등
- 체크리스트 없음, 문서화 최소
- 목적: 빠른 피드백

#### 안내 리뷰 / 워크스루 (Walkthrough)

- 작성자가 리뷰어들에게 내용을 설명
- 토론, 아이디어 교환 중심
- 형식: 비교적 비공식
- 주요 역할: 작성자가 진행

#### 기술 리뷰 (Technical Review)

- 기술 전문가들이 수행
- 기술적 정확성, 표준 준수 확인
- 문서화 있음
- 작성자 참석 필수는 아님

#### 인스펙션 (Inspection) — 가장 공식적

- 가장 형식적인 리뷰 유형
- **역할 분리가 명확함:**

| 역할 | 역할 설명 |
|------|----------|
| 작성자 (Author) | 리뷰 대상 문서/코드 작성자 |
| 진행자 (Facilitator/Moderator) | 회의 진행, 중립 유지 |
| 검토자 (Reviewer) | 결함 발견, 개별 준비 |
| 기록자 (Scribe) | 결함 목록 기록 |
| 관리자 (Manager) | 리뷰 계획 지원 |

**인스펙션 프로세스:**
1. 계획 (Planning)
2. 킥오프 (Kick-off)
3. 개별 준비 (Individual Preparation)
4. 리뷰 세션 (Review Session)
5. 수정 (Rework)
6. 완료 (Follow-up)

---

## 3.3 정적 분석 (Static Analysis)

코드를 실행하지 않고 분석 도구를 사용하여 결함을 찾는 방법.

**도구 예시:**
- SonarQube
- ESLint (JavaScript)
- Pylint (Python)
- PMD, Checkstyle (Java)

**발견 가능한 결함:**
- 문법 오류 (컴파일 오류)
- 스타일 위반
- 복잡도 측정
- 보안 취약점
- 사용되지 않는 변수/코드

---

## 3.4 리뷰 성공 요소

**리뷰를 성공시키는 요인:**
- 명확한 목적
- 적절한 참가자 선택
- 사전 준비 시간 충분히 제공
- 결함 발견에 집중 (비난 아님)
- 관리자의 지원
- 체크리스트 사용

**리뷰 실패 요인:**
- 너무 많은 범위를 한 번에 리뷰
- 참가자 준비 부족
- 개인 비판 분위기
- 결과 추적 없음
